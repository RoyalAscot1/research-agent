# Lens — AI Research & Sentiment App: Build Summary

## What the app does

Lens is a web app that lets users ask natural language research questions and receive AI-generated reports combining factual web research with public sentiment data from Reddit and Google Trends. Users can follow up on each report with up to 5 questions before starting a new query. All queries and reports are saved to a per-user history.

---

## User journey

1. **Sign in** — Google OAuth via Clerk. Lands directly on the prompt screen.
2. **Prompt screen** — single search bar. User types a query and hits Run. No source configuration — the agent decides automatically.
3. **Progress screen** — live step indicator while the agent runs (Planning → Researching → Sentiment → Writing). Typical run time: 15–40 seconds. User can navigate away; job continues in background.
4. **Chat screen** — the finished report loads as a styled card at the top:
   - Three sentiment score cards (Positive %, Neutral %, Negative %)
   - AI-written summary (3–4 paragraphs combining facts and sentiment)
   - Source cards with per-source sentiment bars
   - Below the report: a chat input for follow-ups, plus 3 suggested follow-up chips generated by the AI
   - Up to 5 follow-up questions allowed. After 5, the input is disabled with a "Start a new query" message.
5. **History screen** — list of all past queries with sentiment badge (Positive / Mixed / Negative), date, and run time. Click any row to reopen the full report and follow-up thread (read-only). Delete individual entries or clear all.

---

## Architecture overview

The app has two separately deployed services:

- **Next.js frontend** — deployed to Vercel
- **FastAPI backend** — deployed to Render as a Docker container

Both share a single Postgres database.

## Database schema (Postgres)

```sql
-- users table synced from Clerk via webhook (Clerk owns auth, Postgres owns app data)
users (id, clerk_user_id, email, created_at)

-- One row per query run
research_jobs (
  id UUID PRIMARY KEY,
  user_id UUID REFERENCES users(id),
  query TEXT,
  status TEXT,  -- pending | running | done | failed
  created_at TIMESTAMPTZ,
  completed_at TIMESTAMPTZ
)

-- Finished report — linked to job
reports (
  id UUID PRIMARY KEY,
  job_id UUID REFERENCES research_jobs(id),
  user_id UUID REFERENCES users(id),
  report_markdown TEXT,          -- the AI-written report
  raw_context JSONB,             -- frozen research payload for follow-ups
  suggested_followups JSONB,     -- 3 follow-up chip suggestions from synthesizer
  sentiment_positive FLOAT,
  sentiment_neutral FLOAT,
  sentiment_negative FLOAT,
  reddit_volume INT,
  source_count INT,
  overall_sentiment TEXT,        -- Positive | Mixed | Negative
  created_at TIMESTAMPTZ
)

-- Follow-up Q&A pairs (max 5 per report)
follow_ups (
  id UUID PRIMARY KEY,
  report_id UUID REFERENCES reports(id),
  user_id UUID REFERENCES users(id),
  question TEXT,
  answer TEXT,
  turn_number INT,               -- 1–5
  created_at TIMESTAMPTZ
)
```

## API endpoints (FastAPI)

```
POST   /queries                        Start a new research job
GET    /jobs/{job_id}/status           Poll job status (returns step + % complete)
GET    /reports/{report_id}            Load a finished report
POST   /reports/{report_id}/followup   Submit a follow-up question (max 5)
GET    /history                        List all reports for the authenticated user
DELETE /history/{report_id}           Delete a report
DELETE /history                        Clear all history for the user
```

## LangGraph agent graph

The agent runs as a directed graph with four nodes:

```
Planner → Researcher → Sentiment → Synthesizer
              ↑____________|
           (re-plan if needed, max 3 iterations)
```

**Planner** — Gemini decides which tools to call and how to decompose the query.

**Researcher** — calls Tavily for web results. Chunks and embeds results into Chroma (tagged with `user_id`). Checks Chroma for relevant prior research before calling Tavily.

**Sentiment** — calls PRAW (Reddit) and pytrends (Google Trends). Scores Reddit posts with VADER. Returns structured sentiment context block.

**Synthesizer** — assembles a prompt from: system instruction + web research chunks (with relevance scores) + sentiment context block + output format instruction. Calls Gemini to write the final 200–300 word report. Also generates 3 follow-up suggestions as JSON in the same call. Saves `raw_context` to Postgres for follow-up use.

**Token budget** — enforce `max_iterations=3` on the graph. Use token counting to prevent runaway Gemini calls.

---

## Follow-up implementation (Option A — stateless re-synthesis)

Follow-ups do NOT re-run the full agent graph. They re-use the frozen `raw_context` saved when the report was written.

On each follow-up:
1. Load `raw_context` from Postgres
2. Load all prior follow-up Q&A pairs for conversation history
3. Pass `raw_context` + conversation history + new question to Gemini (synthesizer only)
4. Save the answer to `follow_ups` table
5. Return answer — typically responds in ~3 seconds

Enforce a hard limit of 5 follow-ups per report at the API level. After 5, return a 403 with a message prompting a new query.

The follow-up prompt instructs Gemini: "Answer using only the research above. If the research doesn't cover this, say so clearly. Do not invent new facts."

```
  Top negative themes: ...

  Search interest: +N% WoW for "query variant"
  Breakout queries: ...

Sentiment note: [Hand-crafted summary of nuances the aggregate score misses]
```

## Key implementation notes

- **Two ORMs, one DB**: Prisma (Next.js/TypeScript) and SQLAlchemy (FastAPI/Python) both point at the same Postgres database. Alembic owns all migrations — configure Prisma to use the existing schema, not manage its own.
- **pytrends rate limits**: Add `time.sleep(1)` between calls. Wrap in try/except and return empty Trends data if it fails — never block the full report on a Trends failure.
- **Chroma user filtering**: Every Chroma query must include a `where={"user_id": user.id}` filter so users only retrieve their own prior research.
- **Sentiment cache (Redis, post-v1)**: Key: `sentiment:{sha256(query)}`. TTL: 6 hours. Skip Reddit + pytrends entirely if cache hit.
- **Progress reporting**: Store current step name in Redis (or Postgres if Redis not available) keyed by `job_id`. The polling endpoint reads and returns it.
- **VADER upgrade path**: Start with VADER for speed. Upgrade to `cardiffnlp/twitter-roberta-base-sentiment` if sarcasm/slang causes poor results.
- **Report overall sentiment**: Derive from scores — Positive if positive% > 55%, Negative if negative% > 30%, else Mixed.
- **Follow-up chips**: Synthesizer returns a JSON block at the end of every report: `{"followups": ["...", "...", "..."]}`. Frontend strips this from the display and renders as clickable chips.
- **Clerk auth**: Use `@clerk/nextjs`. Configure `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY` as environment variables on Vercel. Sync Clerk users into the `users` table via a Clerk webhook on `user.created`.
- **CORS**: Configure FastAPI CORS middleware to allow requests from the Vercel frontend domain.
- **Environment variables**: Never hardcode API keys. Use Render environment variables for the backend (GEMINI_API_KEY, TAVILY_API_KEY, REDDIT_CLIENT_ID, REDDIT_CLIENT_SECRET, DATABASE_URL). Use Vercel environment variables for the frontend (NEXT_PUBLIC_API_URL, NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY, CLERK_SECRET_KEY).

## Build order (recommended)

1. Postgres schema + Alembic migrations (done)
2. FastAPI skeleton with all endpoints returning stubs (done)
3. Clerk — auth flow end to end (done)
4. LangGraph graph — single node (Gemini only, no tools) to validate wiring (done)
5. Add Tavily researcher node
6. Add PRAW + VADER + pytrends sentiment node (combined — no useful intermediate state between the two)
7. Synthesizer prompt — iterate on 20+ real queries until quality is consistent
8. Next.js frontend — prompt screen + progress polling (moved earlier — needed to evaluate report quality at scale)
9. Next.js frontend — chat screen (report card + follow-up chat)
10. Follow-up endpoint
11. Next.js frontend — history screen
12. Docker + GitHub Actions + Render deploy
13. Chroma integration (post-v1— adds complexity without affecting core product quality)
14. Redis caching (post-v1)
